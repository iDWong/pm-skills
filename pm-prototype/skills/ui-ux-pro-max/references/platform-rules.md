# 多端适配规则与一致性审查

八端的硬规则、平台差异怎么出稿、以及跨端一致性审查（`CONSISTENCY.md`）的规格。
品牌层与组件层的内容规格见 `design-system.md`，交付流程与产物结构见 `prototype-delivery.md`。

## 0 · 平台差异怎么出稿：独立页面，不做切帧

平台差异**不是状态**——真实用户不会在 iOS 和 Android 之间切换，所以它既不能挂帧（铁律 8 已废除出稿帧），
也不该做成工具条开关。规则：

1. **只在差异点真实存在的页面出多版**，其余页面三端共用一版。差异点只有六类（见第 1–3 节末的对照表）：
   导航模式、返回逻辑、权限弹窗、通知、深色模式、折叠屏与平板。
2. 多版走**独立文件 + 独立卡片**：`app-01-login-ios.html` / `app-01-login-android.html` / `app-01-login-hmos.html`，
   墙上同一组内并排，卡片图注写 `iOS` / `Android` / `HarmonyOS` + PRD 章节号。
3. 共用版不加后缀。**一个页面要么只有共用版，要么三端齐全**，不许只出 iOS 版就算完。
4. 每一处差异都要在 `CONSISTENCY.md` 里有一行，并注明**是平台规范要求还是自选**（判据见第 9 节）。

## 1 · iOS（HIG）

| 项 | 必须做到 | 判据 |
| --- | --- | --- |
| 安全区 | 顶 44 / 底 34（393×852 基准），内容不压刘海与 Home Indicator | 底部固定条 `padding-bottom: env(safe-area-inset-bottom)` |
| 手势返回 | 左缘 20pt 内**不放可横滑控件**（轮播、横滑行、滑动删除都要避开）| 横滑行左边距 ≥20pt |
| 导航 | TabBar ≤5 项且**图标带文字**；层级页用返回箭头 + 上级页名，不用「返回」二字 | TabBar 项数与文案 |
| 大标题 | 列表类首屏用 Large Title，滚动后收成普通导航栏 | 滚动前后各截一张 |
| 图标 | 优先 SF Symbols，**给出符号名**（`chevron.left`）；自绘图标要与 SF 的线宽视重一致 | HANDOFF 图标表带 SF 名一列 |
| 触控 | 最小 44×44pt，间距 ≥8pt | 见 `pro-rules.md` |
| 层 | 破坏性操作用 Action Sheet（底部升起），信息确认用 Alert（居中）——别互换 | 逐个层核对 |
| 权限 | 系统弹窗**前**要有自解释前置页说明用途，拒绝后给设置页入口 | 权限流程在 `FLOWS.md` 里两条分支齐 |

## 2 · Android（Material Design 3）

| 项 | 必须做到 | 判据 |
| --- | --- | --- |
| 导航 | Bottom Navigation（3–5 项）；**系统返回键与手势条必须有处理**，返回栈层级写进 `FLOWS.md` | 每页都答得出「按返回去哪」 |
| 手势导航条 | 底部预留 48dp，内容不被遮 | 底部固定条高度 |
| 反馈 | 用 Snackbar（带动作、可撤销），**不要照搬 iOS 的居中 Toast** | 全站反馈层类型 |
| FAB | 主操作用 FAB 时，位置与滚动收起行为写死 | 滚动前后表现 |
| 动态色 | 是否启用 Material You 动态取色要**明确写**；启用则给品牌色的兜底方案 | MASTER.md 里一句话结论 |
| 权限 | Runtime 权限：首次请求前给说明，二次拒绝后走设置页；**不要在冷启动一次性请求全部** | 权限流程分支 |
| 状态栏 | 沉浸式时给内容顶部安全内边距，浅色壁纸下图标要反色 | 浅深两档各看一次 |

## 3 · HarmonyOS（ArkUI）

| 项 | 必须做到 | 判据 |
| --- | --- | --- |
| 卡片化 | 内容以卡片为基本容器，圆角与留白取 ArkUI 尺度，不直接套 Android 的平铺列表 | 首页与列表页 |
| 服务卡片 | 至少出 **2×2 与 2×4** 两种规格，内容是「可直接用的信息 + 一个动作」，不是应用图标放大 | 卡片稿随包交付 |
| 一多适配 | 按一次开发多端部署的栅格（sm/md/lg）给断点行为，平板与折叠屏展开态**要出稿** | 展开态单独一张卡 |
| 返回 | 侧滑返回 + 导航返回并存，行为一致 | 返回逻辑表 |
| 原子化服务 | 若有免安装入口，给出入口位置与首屏内容 | PRD 有则必出 |

**三端差异只允许出现在这六处**（其余保持一致，否则进 `CONSISTENCY.md` 的「冲突」列）：
导航模式 · 返回逻辑 · 权限弹窗 · 通知 · 深色模式 · 折叠屏与平板。

## 4 · 微信小程序（WeUI）

| 项 | 必须做到 | 判据 |
| --- | --- | --- |
| 胶囊避让 | 右上角胶囊 87×32pt，自定义导航栏高度 = 状态栏高 + 44pt，**右侧 ≥100pt 内不放操作元素** | 自定义导航页逐个量 |
| 组件基线 | 基础控件对齐 WeUI 视觉（按钮高度、列表行高、表单行结构），不把 App 的控件直接搬过来 | 与 WeUI 并排比对 |
| 分包 | 主包 ≤2MB、总包 ≤20MB；**首屏只依赖主包**，设计上要能接受「次级页面加载时有过渡」 | 分包方案写进 HANDOFF |
| 登录授权 | **必须由用户点击触发**，不在进入即弹；给出**拒绝后的降级路径**（游客可浏览到哪一步） | 授权流程两条分支 |
| 支付 | 调起前的确认层、支付中、成功 / 失败 / 取消三态齐 | `FLOWS.md` 支付条 |
| 订阅消息 | 申请时机绑定在用户完成某动作后，给出「已订阅 / 未订阅」两种后续表现 | 两态各一张 |
| 分享 | 分享卡片 5:4 出稿（标题 / 图 / 路径），朋友圈单独一版；**分享出去打开的落地页要能处理未登录** | 卡片稿 + 落地页 |

## 5 · 支付宝小程序（Ant Design Mini）

组件基线换成 Ant Design Mini（按钮、列表、表单的视觉与微信不同，**不要一套皮套两端**）。
另有四个微信没有的入口，PRD 点名了就必须出稿：**芝麻信用**（授权与分数展示口径）、**花呗**（分期选择与费率展示）、
**会员体系**（等级与权益位）、**生活号**（关注引导位置与时机）。
授权时机与降级、支付三态、分包的要求与第 4 节相同，不再重复。

## 6 · 移动端 H5

| 项 | 必须做到 | 判据 |
| --- | --- | --- |
| 断点 | **320 / 375 / 414 / 768** 四档都要过，320 是底线（不许横向滚动）| 四档逐一拉过 |
| 字体缩放 | 用 `rem` 或 `vw` 基准；**系统最大字号下不破版**（至少测到 200%）| 放大后截图 |
| 安全区 | 刘海屏用 `env(safe-area-inset-*)`，底部固定条必须避让 | 固定条样式 |
| 横屏 | 明确「支持 / 锁定竖屏」；支持则出横屏稿 | 一句话结论 + 稿 |
| 弱网 | 首屏骨架 + 超时兜底（给重试），**图片懒加载**且预留尺寸防跳动 | 图片带宽高或 `aspect-ratio` |
| 降级 | 无原生能力时的替代：分享→引导「点右上角」或复制链接、支付→跳收银台页、登录→短信验证码 | 三条各一条流程 |
| 嵌 WebView | 在 APP 内打开时隐藏自有顶栏、复用宿主返回；独立打开时显示自有顶栏 | 两种入口各一张 |

## 7 · WEB 官网

| 项 | 必须做到 | 判据 |
| --- | --- | --- |
| 栅格 | 12 列（内容站）或 24 列（信息密集），最大内容宽 1200–1440，两侧留白随断点变 | 栅格线叠图检查 |
| 首屏 | Hero 结构固定：一句价值主张 + 一句支撑 + **主 CTA + 次 CTA** + 视觉；首屏内必须出现主 CTA | 1280×900 首屏截图 |
| 结构 | 价值主张 → 核心功能 → 客户 logo → 数据 → 案例 → CTA → Footer，缺哪节要说明理由 | 页面分节 |
| 动效 | 滚动视差与微交互只做**锦上添花**，`prefers-reduced-motion` 下全部降级为淡入 | 降级测一次 |
| SEO | 语义标签（`header/nav/main/article/footer`、**每页唯一 h1**）、`title` 与 `meta description`、
Open Graph、结构化数据（Organization / Product / FAQ）、`sitemap.xml` 与 `robots.txt` 规划 | 逐项 grep |
| 性能 | LCP 元素指明是谁并预加载；图片 WebP/AVIF + 响应式 `srcset`；CDN 与字体子集化方案写进 HANDOFF | HANDOFF 第 7 节 |

## 8 · WEB 运营管理系统

| 项 | 必须做到 | 判据 |
| --- | --- | --- |
| 信息密度 | 紧凑档：表格行高 40–48px、控件高 32px、区块间距 16px；**同一屏能看到 ≥10 行数据** | 1440×900 下数一遍 |
| 表格 | 固定表头 + 固定首列（操作列右固定）；列宽策略、排序三态、行选中与批量条 | 滚动到底与右侧验 |
| 效率 | 常用操作给快捷键（至少搜索 `/`、保存 `⌘S`、关闭 `Esc`）；多标签页方案（是否保留、上限、关闭策略）写死 | 一句话结论 + 稿 |
| 权限 | RBAC 三级：**菜单级 / 按钮级 / 数据级**。五角色（超管 · 运营 · 客服 · 财务 · 审核）逐一给权限矩阵；
数据级要写明「看得到哪些行、脱敏到什么程度」 | 权限矩阵表 + 演示账号 |
| 状态 | 空 / 错 / 加载 / **无权限**四态逐页覆盖；无权限态要区分「没菜单」与「有菜单无按钮」 | 状态矩阵 |
| 主题 | 暗色与亮色两档都出稿，暗色不是把背景调黑——阴影换亮边、图表色需重新验对比度 | 两档各截图 |
| 其余三条 | 顶栏三件套、抽屉开合契约、敏感数据脱敏与申请解密，见 `prototype-delivery.md`「WEB端运营管理系统专项」 | 那一节 |

## 9 · 一致性审查（`CONSISTENCY.md`，覆盖 ≥2 端时必交）

### 9.1 一致性矩阵

六个维度 × 项目实际覆盖的端，逐格填 **一致 / 差异 / 冲突**：

| 维度 | 看什么 |
| --- | --- |
| 品牌 | logo 用法、品牌色出现位置、语气 |
| 色彩 | 同一语义在各端的色值是否同源于 `tokens.json` |
| 字体 | 字阶与行高的换算关系（pt ↔ dp ↔ px）是否一致 |
| 组件 | 同名组件的变体、尺寸档、八态是否同构 |
| 交互 | 同一动作的反馈方式（Toast / Snackbar）、层的关闭方式、返回逻辑 |
| 文案 | 同一功能的用词（「确认」还是「确定」）、错误提示口径 |

### 9.2 差异合理性判定

| 判定 | 依据 | 处理 |
| --- | --- | --- |
| **合理差异** | 平台规范硬要求（iOS Action Sheet vs Android Snackbar、胶囊避让、返回键）| 保留，在矩阵里注明依据条款 |
| **可接受差异** | 能力差异导致（H5 无原生分享 → 引导复制链接）| 保留，必须写降级说明 |
| **冲突** | 无平台依据的漂移：同一语义色不同值、同一按钮两种圆角、同一功能两种文案 | **必须统一**，列进改进项并给责任端 |

判据一句话：**说不出平台规范条款或能力限制的差异，一律按冲突处理。**

### 9.3 改进建议三件

1. **组件统一方案**：冲突项归并到同一份组件规格，写明「以哪一端为准、其余端怎么改」。
2. **令牌同步方案**：见 `design-system.md` 第三节——单一源 + 各端生成脚本；补一条「令牌改动的通知链路」。
3. **多端走查清单**：每端一列，逐项打勾，**至少含**：首屏、主流程一条、返回逻辑、深色档、最大字号、
   空/错/加载/无权限四态、权限弹窗、分享或跳转落地。走查记录只有 `通过 / 不通过` 两个值，不写「基本一致」。
