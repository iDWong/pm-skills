# 文体规范（全形态通用）

本文件的表头、文案范式与禁用写法**五种形态通用**。形态特有的小节序列与章节见 `profiles/<形态>.md`。

本文件定义 PM-PRD-Spec 的**全部标准表头、文案范式与禁用写法**。Step 4 动笔前通读一遍；写作过程中按需回查。

---

## 一、文档骨架

文档标题（H1）取文件名去掉日期与版本号的部分，即 `{客户名称}{项目名称}{形态}产品需求文档`；形态五选一：后台管理 / APP / H5 / 小程序 / 官网。落盘路径与版本号规则见 `SKILL.md` Step 7。

```
{客户名称}{项目名称}{形态}产品需求文档

目录（自动生成，导出 Word 时保留）

0 系统简介          ← 开篇必写，见下「开篇三节」
0.1 设计与交互      ← 视觉与交互基调，按形态各一段 + 通用交互
0.2 产品边界        ← 范围边界，逐条列
0.3 多语言版本（如有）   ← 多语言范围、切换方式、配置形式
1 登录功能
  1.1 功能概述
  1.2 登录界面UI设计
  1.3 登录流程
  1.4 错误提示规范
  1.5 安全防护机制
      1.5.1 防暴力破解策略
      1.5.2 会话管理
2 仪表盘
  2.1 汇总统计
  2.2 趋势统计
3 系统设置
  3.1 用户管理
      3.1.1 功能概述
      3.1.2 数据筛选
      3.1.3 数据展示
      3.1.4 新建用户
      3.1.5 界面与交互规范
  3.2 角色管理
  3.3 系统日志
4 {业务域一}
5 {业务域二}
6 数据统计
7 订单管理
附录A 全局错误提示规范
附录B 操作类型枚举
附录C 数据时效与统计口径
附录D 非功能需求
附录E 待确认项清单
```

**层级规则**
- 一级 = 功能域（对应左侧一级菜单）
- 二级 = 页面（对应二级菜单或独立页面）
- 三级 = 页面内的固定小节（功能概述 / 数据筛选 / 数据展示 / 新建X / 界面与交互规范）
- 每个页面的「功能概述」小节末尾必须挂一张**页面原型图**，弹窗单独一张（见 `wireframe.md`）

**两样东西别混称**（同一交付包里会同时出现，评审时问过不止一次）：

| 东西 | 正式叫法 | 在哪 | 谁出 |
| --- | --- | --- | --- |
| PRD 正文里那张静态图 | **页面原型图** | 嵌在每个页面「功能概述」小节末尾 | 本技能（Step 4） |
| 可点、可交互的独立 HTML | **UI/UX设计稿**（简称设计稿） | `design-system/<项目slug>/`（三张预览墙 + 全屏页） | `ui-ux-pro-max`（Step 8） |

正文、图注、README、交付说明与产物页面文案都按这张表用词。触发词（全技能统一）：**设计稿 / 高保真原型 / 可点原型 / 交互原型 / 预览墙**——用户说其中任意一个都是指后者，照旧识别，不用纠正用户的说法。
- 最深到三级；再往下用加粗小标题，不要出现四级编号

### 开篇三节（正文第一个功能域之前，缺一不可）

评审时最先被问、也最容易漏的三件事。写在目录之后、功能域之前：

**① 系统简介**——一段话（3–5 句）说清：这是什么、给谁用、对标/参考谁、**做了哪些简化**、由哪几个端组成。
写法示例：「XX 系统是一套面向内容创作者和读者的信息流平台，参考微信公众号的信息架构，但做简化处理：
不依赖邮箱和手机号注册，创作者申请免审核直接通过。系统包含用户使用端、创作者平台、管理后台三端。」
**"参考谁 + 简化了什么"这半句不能省**——它替开发挡掉一半"为什么不做成微信那样"的追问。

**② 设计与交互**——全局视觉与交互基调，**按端/形态各写一段**，每段四行：

| 行 | 写什么 | 例 |
| --- | --- | --- |
| 整体布局 | 导航位置、内容区、留白、有无底部导航 | 顶部栏简洁，内容区白底，页面左右留白 16px，无底部导航栏 |
| 色彩 | 打底 / 点睛 / 警示 / 归零四种语义色 | 深灰蓝打底，暖橙点睛，朱红警示，绿色归零 |
| 核心页面 | 列出页面名 + 一句风格要求 | 消息列表、文章详情、搜索、我的，风格统一，内容优先 |
| **一句话** | **8 个词以内的基调速记** | 白底卡片，圆角轻分割，线性图标，内容优先，干扰最少 |

末尾再加一段 **通用交互**（全端共用）：加载态、空状态、提示位置、危险操作、返回行为各一句。
例：「加载用骨架屏，空状态用插画+一句引导，提示用顶部 Toast，危险操作二次确认，返回保留上一页状态。」

> 这一节与每个页面末尾的「界面与交互规范」表**不重复**：这里定**全局基调**（一次），
> 那里给**该页的具体规范 + 依据**（每页一次）。基调先定，后面每页才有的可依。
> 出设计稿时（Step 8）这一节直接变成 `ui-ux-pro-max` 的输入，写得越具体，稿子越不跑偏。

**③ 产品边界**——**逐条列出本期明确排除的功能**，每条一句，标明「后续版本迭代」。
这是范围边界，不是免责声明：**没写进来的争议，最后都会变成返工**。
常见该列而没列的：密码找回、账号注销、举报、意见反馈与客服入口、真实支付（只留记录与统计）、
某类文件格式支持、某类用户通知。
例：「实际的支付功能留到后续版本迭代，本期只要查到支付记录，就有汇总统计。」
> 与附录E「待确认项清单」分工：**本节是已经决定不做的**，附录E 是**还没定的**。别混。

---

**标题写法**：中文标题**以冒号结尾**（`功能概述：`、`数据筛选：`、`新建用户：`），与参考文档一致。

## 二、十五种标准表格

写到对应内容时，**直接套用下列表头，不要自创列名**。

### T1 筛选条件表

| 筛选项 | 控件类型 | 默认条件 | 输入提示文字 | 输入规则 |
| --- | --- | --- | --- | --- |
| 用户名称 | 单行输入框 | 无 | 请输入用户名 | 限 20 个字符以内，只能是字母或字母+数字，禁止特殊符号 |
| 用户状态 | 下拉选择框 | 全部 | 无 | 可选择：全部 / 启用 / 停用 |
| 创建时间 | 日期区间选择器 | 默认选中近 7 天 | — | 最大范围可选 30 天 |

- 控件类型只用这批词：`单行输入框`、`多行文本域`、`数字输入框`、`数字区间输入框`、`下拉选择框`、`多选下拉`、`搜索+下拉`、`单选按钮`、`复选框`、`开关`、`日期选择器`、`日期区间选择器`、`时间范围选择器`、`树形结构`、`文件上传`、`只读展示`。
- 无默认值写 `无`，不适用写 `—`。
- 精确/模糊搜索必须写明：`支持按剧名模糊搜索`、`精确搜索`。

### T2 列表字段表

| 字段名称 | 字段说明 | 示例值 |
| --- | --- | --- |
| 日志ID | 全局唯一编号 | 20260902001234 |
| 操作时间 | 精确到毫秒的时间戳 | 2026-09-02 14:32:15 |
| 用户 | 被操作用户的昵称 + UID（点击可跳转至用户画像） | 追剧小能手 (U-100886) |
| 操作 | 可进行的操作 | — |

- 三列是下限。需要区分展示样式时加第四列 `展示规则`（`可复制`、`标签样式`、`YYYY-MM-DD HH:mm`、`数字，保留两位小数`）。
- **操作列在表格里只列名字，具体行为在表格下方逐条展开**：

```
点击【查看详情】后打开：用户画像详情。
点击【编辑标签】后打开标签选择弹窗，可选择所有已创建好的标签，支持多选。
点击【删除】后打开二次确认弹窗（文案见下）。
```

- 表格后必须补两句：分页规则、导出规则。
  - `数据超过 10 条记录后进行分页。`
  - `数据可根据查询条件导出 .xlsx 文件。`（无导出就写"本页不提供导出"）

### T3 表单字段表

| 字段名称 | 控件类型 | 是否必填 | 输入提示文字 | 输入提示/规则 |
| --- | --- | --- | --- | --- |
| 用户名称 | 单行输入框 | 是 | 请输入用户名 | 限 8–20 个字符；只能是字母或字母+数字，禁止特殊符号 |
| 用户密码 | 单行输入框 | 是 | 请输入用户密码 | 暗文显示，可切换明文；限 8–20 个字符；只能是字母或字母+数字 |
| 角色名称 | 下拉选择框 | 是 | 请选择角色 | 可选择所有已创建的角色 |
| 用户状态 | 单选按钮 | 是 | 无 | 启用 / 停用二选一，默认选中：启用 |

- 是否必填只写 `是` / `否`。
- **字段有唯一性约束时另起一列 `唯一性`（`是`/空）**，不要只塞在规则里——唯一性决定后端建索引与查重接口，
  埋在长句里开发会漏。账号、用户名、编码、手机号这类一律显式标出。
- 条件显示的字段必须写清条件：`仅当上传方式="上传视频"时显示`。
- 文件类字段写清格式与体积：`mp4，≤100MB，拖动或点击上传`。
- **需要解释"为什么这么设计"时加一列 `策划说明`**（可选列，只在有非显然决策时用）：
  `密码框支持粘贴 → 方便使用密码管理器`、`回车触发登录 → 提升运营日常操作效率`、
  `仅存账号不存密码，有效期30天 → 安全与便利的折中`。写了这列，评审时少一轮"为什么不…"。

### T3b 数据规范表（面向后端建表，与 T3 分工）

T3 写的是**界面怎么填**（控件、提示文字、输入规则），后端建表还缺三样：**数据类型、默认值、长度上限**。
需要直接支撑建表与接口定义时（要接 `req-doc` 转 SRS、或要交 `lld-design` 做表结构），在 T3 之外补这张：

| 字段名 | 数据类型 | 长度/大小 | 必填 | 唯一 | 默认值 | 格式 | 校验 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| account | string | 20 | 是 | 是 | — | 字母开头，字母+数字 | 注册时查重，重复报「该账号已被注册」 |
| balance | decimal(12,2) | — | 是 | 否 | 0.00 | 两位小数 | 不允许为负；扣减前校验余额 |
| status | enum | — | 是 | 否 | normal | normal / disabled | 枚举外的值拒绝写入 |
| avatar_url | string | 500 | 否 | 否 | 空串 | URL | 非图片域名拒绝 |
| created_at | datetime | — | 是 | 否 | 当前时间 | YYYY-MM-DD HH:mm:ss | 只读，不接受前端传值 |

- **数据类型用后端听得懂的词**：`string` / `int` / `bigint` / `decimal(p,s)` / `boolean` / `enum` / `datetime` / `json`。
  不要写"文字""数字"——那是 T3 的语言，不是这张表的。
- **默认值必须给**，没有默认写 `—`；空串、`0`、`null` 是三个不同的默认值，别混着写。
- 金额一律 `decimal`，**不许 float**；时间一律 `datetime` 并写明时区口径（默认按服务器时区就写明）。
- `created_at` / `updated_at` 这类系统字段也要列，并注明**只读、不接受前端传值**。
- 与 T3 的分工：**T3 给前端做表单，T3b 给后端建表**。同一个字段两张表都出现是正常的，
  但**必填与唯一性两列必须一致**——对不上就是文档自相矛盾，自查时会被逮到。
- 纯展示型页面（列表、详情、看板）不需要这张表；**有写入的页面（新建/编辑/提交）建议给**。

### T4 交互与校验表

| 触发时机 | 校验规则 | 用户提示 | 处理方式 |
| --- | --- | --- | --- |
| 输入等级名称时 | 同一平台内名称是否重复 | 名称已存在，请重新输入 | 阻止提交，高亮字段 |
| 输入门槛金额时 | 是否 ≤ 上一等级门槛 | 最低消费门槛必须高于上一等级 | 阻止提交，高亮字段 |
| 点击【确认创建】时 | 所有必填字段是否已填 | 聚焦到第一个未填字段，显示对应提示 | 阻止提交 |

- 处理方式用词：`阻止提交，高亮字段`、`阻止提交`、`仅提示不阻断`、`按钮置灰`、`自动纠正为合法值`。
- **每个表单至少 3 条校验**：唯一性、字符/数值边界、必填聚合校验。

### T4b 场景反馈表（T4 的广角版，交互密集的页面用它）

T4 只覆盖**校验**，但一个登录页真正要写的远不止校验——成功、锁定、跳转、重复提交都得有交代。
交互分支多的页面（登录注册、支付、审核、提交类流程）在 T4 之外再给一张两列表，**把所有分支一次列全**：

| 场景 | 反馈 |
| --- | --- |
| 账号格式错误 | 实时提示「账号需字母开头，仅含字母和数字」 |
| 账号已存在 | 提交后提示「该账号已被注册，请更换」 |
| 账号或密码错误 | 统一提示「账号或密码错误」，**不区分具体原因** |
| 连续错误 | 5 次错误后锁定 15 分钟 |
| 注册成功 | 提示「注册成功」，自动跳转首页 |

- 两列就够，**别硬套 T4 的四列**——这张表的价值是"分支一个不漏"，不是每条都写处理方式。
- **成功态必须写**：只写失败是最常见的漏项，开发会自己编一个跳转。
- 安全相关的反馈要写明**是否模糊化**（「不区分具体原因」），这是防撞库的要求，不是文案偏好。
- 时序相关的写清**阈值与时长**（5 次 / 15 分钟），别写"多次""一段时间"。
- 与 T4 的分工：**T4 管"字段级校验规则"（给前端做表单），T4b 管"页面级分支反馈"（给测试列用例）**。
  两张都有时不必互相重复，T4b 可只列 T4 没覆盖的分支。

### T5 枚举表

| 显示名称 | 说明 |
| --- | --- |
| 支付未到账 | 用户已扣款但平台未收到回调，最常见场景 |
| 客服补偿 | 因平台体验问题（如卡顿、音画不同步）给用户的补偿 |
| 其他 | 需在备注中说明具体原因 |

带场景的枚举加第三列 `典型场景`：

| 操作类型 | 说明 | 典型场景 |
| --- | --- | --- |
| 新增 | 创建新资源 | 新建剧集 / 新建用户 |
| 审核 | 审核通过 | 剧集审核通过 |
| 导出 | 导出数据 | 导出订单报表、用户列表 |

- 有 `其他` 选项的枚举，必须同时在表单表里写"选择'其他'时备注强制必填"。
- 枚举会随业务变化时标注：`（随实际功能有所调整）`。
- **状态类枚举的「说明」必须是可计算的判定标准，不是形容词**——写成人话开发就得来问一遍：

| 反例（不可计算） | 正例（可计算） |
| --- | --- |
| 活跃：经常使用的用户 | 活跃：近 7 天有客户端与服务端交互 |
| 沉默：不太活跃 | 沉默：8~30 天无客户端与服务端交互 |
| 流失：很久没来了 | 流失：超过 30 天无客户端与服务端交互 |

  判定依赖某个行为时，把**行为本身**也定义掉（例：「观看」= 完整看完一篇，同一人同一篇只算一次；
  全文阅读的判定按文章/图片/视频三类分别给条件）。**状态能不能算出来，是这张表唯一的验收标准。**

### T6 错误提示规范表

| 错误场景 | 前端提示文案 | 提示位置 | 后端日志记录 |
| --- | --- | --- | --- |
| 账号为空 | 请输入账号 | 输入框下方 | 不记录 |
| 账号不存在或密码错误 | 账号或密码错误，请重新输入 | 弹窗提示 | 记录"登录失败（账号/密码错误）" |
| 系统内部错误 | 系统繁忙，请稍后再试 | 弹窗提示 | 记录详细错误堆栈 |

- 提示位置只用：`输入框下方`、`弹窗提示`、`顶部 Toast`、`表格内联`、`页面级空态`。
- 安全相关错误一律**模糊提示**，并在说明中写明原因：`（统一模糊提示，不暴露具体原因）`。

### T7 交互规则表（危险操作）

| 规则 | 说明 |
| --- | --- |
| 仅可退一次 | 已退款的订单，【发起退款】按钮置灰或隐藏，不可重复操作 |
| 金额校验 | 退款金额 > 实付金额 → 前端拦截，提示"退款金额不能超过实付金额" |
| 二次确认弹窗 | 点击【确认退款】后，弹出二次确认弹窗，展示完整摘要：即将对订单【WX202609011432001】发起退款 ¥0.99，并回收该剧集权益。确认继续吗？ |
| 实时生效 | 确认后用户端立即获得权限（无需重启 APP），通过 WebSocket 推送权益变更 |

### T8 数据变化表

| 数据项 | 变化说明 |
| --- | --- |
| 订单状态 | 从 支付成功 变为 已退款 |
| 累计消费金额 | 扣减退款金额 |
| 已购剧集总数 | 如果该剧仅通过此订单获得，退款后不再拥有该剧权益 → -1 |
| 操作日志 | 记录操作人、操作时间、用户、订单号、退款金额、退款原因、渠道退款流水号 |

**任何写操作都要有这张表。** 开发靠它判断要改哪些字段、要不要发消息。

### T9 失败处理表

| 失败场景 | 系统行为 |
| --- | --- |
| 支付渠道余额不足 | 提示"支付渠道余额不足，请联系财务充值"，订单状态不变 |
| 支付渠道接口超时 | 提示"退款接口超时，请稍后重试"，订单状态不变 |
| 渠道返回未知错误 | 提示"退款失败，错误码：XXXX"，订单状态不变 |

调用外部系统（支付、短信、推送、审核）的操作，**必须**有这张表。

### T10 权限模型表

| 层级 | 定义 | 示例 |
| --- | --- | --- |
| 用户（User） | 具体操作后台的个人账号 | zhangsan@company.com |
| 角色（Role） | 权限的集合，可分配给多个用户 | 内容审核专员、财务主管 |
| 权限（Permission） | 对某个菜单或菜单中功能的使用 | 会员列表、订单记录 → 退款 |

配套写清三条：初始超级管理员的产生方式、同层数据是否共享、菜单权限树的父子勾选联动。

### T11 安全防护表

| 防护措施 | 具体规则 | 触发后的处理 |
| --- | --- | --- |
| 登录失败次数限制 | 同一账号 5 分钟内连续失败 ≥ 5 次 | 锁定该账号 15 分钟（返回"账号已被临时锁定"） |
| Access Token 有效期 | 2 小时 | 超过 2 小时需重新登录或刷新 Token |
| 闲置超时 | 30 分钟无任何操作（无接口请求） | 自动登出，前端跳转至登录页 |

### T12 时间筛选器表（指标分析页专用）

| 选项 | 说明 | 默认 |
| --- | --- | --- |
| 昨日 | 昨日单日完整数据 | — |
| 近 7 天 | 最近 7 天（不含今天） | 默认 |
| 近 30 天 | 最近 30 天（不含今天） | — |
| 自定义 | 手动选择起止日期（不能选择今日） | — |

表下必须补一句影响范围：`影响范围：新增用户、活跃用户、趋势图受时间筛选器控制（界面有说明）。`

### T13 界面与交互规范表（本技能增量）

| 维度 | 规范 | 依据 |
| --- | --- | --- |
| 表格响应式 | 表格外层 `overflow-x: auto`，最小宽度 1080px；窄屏不换行不截断 | ux/Responsive/Table Handling |

## 三、文案范式

### 入口路径（形式随形态，规则统一）

| 形态 | 写法 |
| --- | --- |
| Web 运营管理系统 | `功能入口：管理后台 → 系统设置 → 用户管理 → 【新建用户】` |
| 移动端 APP | `页面入口：App → 首页Tab → 内容卡片点击 → 内容详情页` |
| 小程序 | `页面入口：小程序 → 首页tabBar → 商品卡片点击 → 商品详情页` |
| 移动端 H5 | `页面入口：微信分享卡片 → 落地页 → 【立即参与】→ 活动页` |
| Web 官网 | `页面入口：官网 → 顶部导航【产品】→ 功能介绍页` |

- 分隔符固定用 `→`（全角箭头，两侧留空格）。
- 按钮名用 `【】`：`【新建用户】`、`【查看详情】`、`【确认补发】`。
- 弹窗打开方式要写：`点击【新建用户】后，从屏幕中间弹出表单窗口。`

### 二次确认弹窗

必须写成**完整可上线的整句**，包含：动作 + 对象（带 `【】`）+ 后果 + 反问。

```
即将对【架空历史】分类进行删除，删除后将影响所有已关联的剧集。确认继续吗？
即将为用户【追剧小能手】补发【《前夫跪求复婚》全集】，确认继续吗？
即将对订单【WX202609011432001】发起退款 ¥0.99，并回收该剧集权益。确认继续吗？
```

### 状态与操作的联动

```
禁用/启用：状态为启用时，按钮显示"禁用"，点击后状态变更为禁用，反之一样。需要二次确认提示弹窗。
【退款】只有支付成功状态的订单可见，并可以操作；操作后修改订单状态为：已退款。
【补单】只有非支付成功状态的订单可见，并可以操作；操作后修改订单状态为：支付成功。
```

### 指标卡九行式

每个指标卡固定写这九行（不适用的写"不适用"，不要整行省略）：

```
总收入：
  定义：平台累计到昨日的收入金额（所有已支付订单金额总和，不含退款）
  时间口径：累计，不受顶部时间筛选器影响
  计算方式：所有已支付订单的金额总和 - 退款总金额
  主数字格式：金额格式，保留两位小数，千位分隔符（如 125,680.50）
  环比对比：环比上月（自然月同期对比）
  环比计算：（本月累计收入 - 上月累计收入）/ 上月累计收入 × 100%
  环比展示：正增长绿色↑，负增长红色↓，单位百分比
  展示文案：环比上月 +18%
  特殊处理：若上个月无数据，显示"—"
```

**受筛选器影响的指标**额外补一段不同范围的环比口径：

```
  不同时间范围的环比口径：
    昨日 → 较前日
    近 7 天 → 较上一个 7 天（不含今天）
    近 30 天 → 较上一个 30 天（不含今天）
    自定义 → 较上一个等长周期
```

**百分比类指标的环比是"百分点差值"，不是百分比变化率**——必须写清楚，这是最常见的口径事故。

### 图表规格

```
收入趋势：
  图表类型：折线图 + 面积图效果（渐变填充）
  数据维度：每日收入金额
  横轴：日期（按时间筛选器范围，不含今日）
  纵轴：收入金额
  数据点：每天 1 个数值，用圆点标记
  面积填充：折线下方渐变半透明填充，增强视觉层次
  交互：鼠标悬停显示具体数值（日期 + 金额）
  统计口径：已支付订单金额 - 当日退款
  时间范围：受顶部时间筛选器控制
  数据说明：展示筛选范围内每一天的收入金额
  空数据表现：无数据时显示空态插图 + 文案"当前筛选条件下暂无数据"
```

### 数据时效声明

涉及统计的页面开头必须写：

```
今日数据不统计，实时查询消耗过大，数据采用定时器跑批后存入数据库。
数据采用每日 02:00 进行统计。
```

### 边界条件五问（每个 🔴 页面逐条过，不适用也要写明）

「页面状态六态」管的是**这一屏长什么样**，边界条件管的是**数据与并发出意外时怎么办**——
两件事，别互相顶替。六态齐了仍然会漏下面这五条，它们是评审与测试最爱问的：

| # | 边界 | 要答的问题 | 不写的后果 |
| --- | --- | --- | --- |
| 1 | **内容为空 / 超长** | 字段上限多少？超了截断、报错还是禁止输入？列表 0 条与 10 万条分别什么样？ | 前端自己定上限，与后端字段长度对不上，线上报 500 |
| 2 | **网络异常或超时** | 超时阈值多少？自动重试几次？重试期间按钮什么状态？ | 用户狂点提交，产生重复数据 |
| 3 | **无权限** | 整页拦截、隐藏入口，还是可见但置灰？提示文案原文？ | 越权入口留在页面上，审计直接判不合格 |
| 4 | **并发操作同一条数据** | 两个人同时改同一条怎么办？后提交覆盖、乐观锁报错，还是锁定？ | 运营互相覆盖对方的修改，且事后查不出 |
| 5 | **数据格式不符** | 上传/导入的文件格式、编码、字段缺失怎么处理？部分成功怎么反馈？ | 导入半途失败，用户不知道哪几行没进去 |

写法：在页面的「危险操作」或「新建/编辑」小节末尾用一个 `**边界条件**` 粗体块逐条给答案，
**不适用的写「不适用（本页只读）」**，不要整条省略——省略与"想过了但不适用"在评审时看不出区别。

### 验收标准（每个 🔴 页面 2–5 条）

放在页面最后一个小节之后，用可勾选清单写，**一条 = 一个可观察的结果**：

```
**验收标准**

- [ ] 在会员列表输入手机号 138****6207 并点击【查询】，1 秒内返回该会员单条记录
- [ ] 对已停用会员点击【积分调整】，按钮置灰且 tooltip 显示「账号已停用，无法调整积分」
- [ ] 提交积分调整时网络断开，显示「网络异常，请重试」且积分余额不变
```

- **句式固定为「做了什么 → 看到什么」**，两边都要具体：`点击【查询】`、`显示「网络异常，请重试」`。
- 禁止写"功能正常""体验流畅""符合预期"——**不可观察的都不算验收标准**。
- 至少覆盖一条**失败路径**，只写正常流的验收标准等于没写。
- 这几条会被 `pm-test-cases` 直接转成测试用例，写得越具体，用例越省事。

## 四、禁用写法

| 禁用 | 改成 |
| --- | --- |
| "提示错误信息" / "给出相应提示" | 写出原文：提示"账号或密码错误，请重新输入" |
| 示例值写 "xxx" / "字符串" / "某某" | 写具体假数据：`COMP20260902001`、`2026-09-02 10:15:23` |
| "支持筛选" | 列出 T1 筛选条件表 |
| "字段若干" / "包含基本信息" | 列出 T2/T3 字段表，一个不漏 |
| "做必要的校验" | 列出 T4 交互与校验表 |
| "展示图表" | 按图表规格九行写 |
| "环比展示" 而不说口径 | 写出环比计算公式和百分点 vs 百分比 |
| 用散段落罗列多个同类项 | 转成表格 |
| 写技术实现（用 Redis 缓存、加索引） | 只写"要求列表首屏 ≤ 2 秒"，实现交给 `lld-design` |
| 用 emoji 当结构图标 | 用文字或说明 SVG 图标族 |
| 页面写完不给 UX 规范段 | 补 T13 |
| 页面写完不配原型图 | 补一张，弹窗单独一张（见 `wireframe.md`） |
| 原型图 PNG 用中文文件名 | 改成纯 ASCII，否则 Word 导出静默丢图 |

## 五、语言风格

- 全中文，专业但不啰嗦；一句话说清一件事。
- 数字、英文、代码与中文之间不强制加空格，但同一份文档内保持一致。
- 金额统一写 `¥` 或 `（元）` 后缀，二选一贯穿全文。
- 时间格式统一：日期 `2026-09-02`，日期时间 `2026-09-02 14:32:15`，列表展示可用 `2026-09-02 10:15`。
- 枚举分隔符统一用 ` / `：`正常 / 已冻结 / 已注销`。
- 范围符号用 `≥ ≤ >` 而不是 `大于等于`。
